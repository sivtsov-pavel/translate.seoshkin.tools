## 🔴 1. КРИТИЧНО: гейт прогрессии отнял доступ у трёх живых учеников

**Это не теория, это состояние прода сейчас.**

Запрос воспроизводит `LESSON_PASSED_HAVING` из `drip.js` (с LEFT JOIN, как в коде) для всех
учеников с прогрессом:

| ученик | курс | уроков с прогрессом | пройдено по новому правилу | первый непройденный | дальний с прогрессом | расписание |
|---|---|---|---|---|---|---|
| 1 (Павел) | 2 | 6 | 4 | 3 | 6 | нет |
| 1 | 5 | 5 | 0 | 12 | 39 | нет |
| **21** | 2 | 12 | **0** | **1** | **15** | **есть** |
| **28** | 2 | 2 | **0** | **1** | 2 | **есть** |
| **31** | 2 | 3 | **0** | **1** | 3 | **есть** |

Механика поломки в `playableLessonIds`:

```js
const gateOpen = doneIdx === 0 || prevPassed
```

У учеников 21, 28, 31 **урок 1 не пройден** по новому правилу (у ученика 21 в уроке 1:
карточек 12 — сделано 2, «выбери ответ» 12 — сделано 0). Цепочка рвётся на первом же звене:
урок 2 закрыт, значит закрыты и все последующие. **Ученику 21 сейчас доступен ровно один
урок — первый, хотя он занимался в двенадцати и дошёл до пятнадцатого.**

Автор в промте писал «у активных учеников 28 и 31 уроки закрылись» — фактический масштаб
больше: закрылось всё, кроме первого урока, и ученик 21 тоже задет.

### Ответ на вопрос «не нужно ли однажды открытый оставлять открытым»

**Да, обязательно.** Но одного этого мало: нужны три уровня, от срочного к правильному.

**Уровень 1 — хотфикс (одна строка, возвращает доступ сегодня):**

```js
// Урок, в котором ученик уже занимался или который прошёл, не закрывается никогда:
// правила прохождения могут меняться, отнимать доступ у занимавшегося — нельзя.
const gateOpen = doneIdx === 0 || prevPassed || passedSet.has(l.id) || touchedSet.has(l.id)
```

`touchedSet` — уроки, где есть хоть одна запись `user_exercise_progress` (один запрос рядом
с `passedRows`). Дешевле и честнее, чем ослаблять правило прохождения.

**Уровень 2 — развести два понятия.** «Пройден» (строгое: карточка + выбор по каждому слову)
годится для отчёта учителя и для *открытия следующего*. Для *сохранения доступа* нужен
«начат». Плюс порог: открывать следующий урок при ≥80% выполнения, а не при 100% — иначе
один забытый элемент блокирует ветку навсегда, а ученик не понимает, чего от него хотят.

**Уровень 3 — хранить факт открытия** (`user_lesson_unlocked`: user_id, lesson_id, opened_at).
Тогда любое будущее изменение правил физически не сможет отнять доступ. Это и есть настоящее
«однажды открытый остаётся открытым»; сейчас доступ вычисляется каждый раз с нуля, и поэтому
уязвим к любой правке формулы.

**Рядом мелкий, но реальный рассинхрон:** в `playableLessonIds` вызывается
`unlockedCount(start_date, weekdays)` без третьего аргумента, то есть по UTC, а в
`runDripPush` — по локальной дате ученика. Для Мюнхена (UTC+2) после 22:00 локальная дата уже
следующая: пуш «открылся новый урок» уходит, а API этот урок ещё не отдаёт. Передавать в оба
места одну и ту же локальную дату.

## 🟠 2. Подтверждено: `upsertLessonWord` уронит обработку урока (но пока не выстрелило)

Автор честно указал место. Проверил базу: **дублей «слово с артиклем / без» сейчас 0**, то
есть бомба заряжена, но не сработала. Сценарий срабатывания:

```js
const upgrade = re.test(wordDe) && !re.test(rows[0].word_de) ? wordDe : rows[0].word_de
await db.query(`UPDATE words SET word_de = $2 ... WHERE id = $1`, [rows[0].id, upgrade, ...])
```

Если в уроке уже есть и «Tisch», и «der Tisch» (две строки), `SELECT ... LIMIT 1` возьмёт
одну из них, а `UPDATE` попытается присвоить ей форму второй → нарушение уникального индекса
`(lesson_id, word_de)` → исключение → падает обработка урока.

Пути, которыми такая пара может появиться, и они все живые:
- копирование учебника (`catalog.adoptTextbook` вставляет слова как есть, без слияния форм);
- ручная правка слова, если где-то меняется `word_de`;
- восстановление старого бэкапа (до введения слияния форм дубли были нормой).

**Второй дефект в том же запросе:** `LIMIT 1` без `ORDER BY` — при нескольких совпадениях
выбор строки недетерминирован, прогоны будут расходиться.

**Правка:**

```sql
-- 1) выбирать предсказуемо: сначала форму с артиклем, потом по возрастанию id
ORDER BY (word_de ~* '^(der|die|das|...)\s') DESC, id
-- 2) UPDATE делать только если целевая форма в уроке не занята другой строкой
UPDATE words SET word_de = $2, ... WHERE id = $1
  AND NOT EXISTS (SELECT 1 FROM words w2
                  WHERE w2.lesson_id = $5 AND lower(w2.word_de) = lower($2) AND w2.id <> $1)
```

Если форма занята — это дубль, и его надо слить (упражнения и прогресс перевести на
каноническую строку, вторую удалить), а не пытаться переименовать. Слияние — отдельная
функция, но без неё вся защита сводится к «не падаем».

## 🟡 4. `speechMatch`: снисходительность есть, и она в неожиданном месте

Проверил на живых примерах (`speechSimilarity`, порог зачёта из `scoreResult`):

| сказано | эталон | сходство | вердикт ученику |
|---|---|---|---|
| чус | Tschüss | 1.00 | отлично ✓ верно |
| их | ich | 1.00 | отлично ✓ верно |
| **да** | **das** | **0.90** | **отлично ← ложный зачёт** |
| бир | Bier | 0.67 | почти (ок) |
| ах | ich | 0.50 | ещё раз ✓ верно |
| мир | Bier | 0.33 | ещё раз ✓ верно |

Виноваты не снятые различия гласных (они как раз работают правильно), а правило подстроки:

```js
if (a.includes(b) || b.includes(a)) return 0.9
```

На словах из 2–3 букв подстрока — это почти всё слово: «да» внутри «дас» → 0.9 → высшая
оценка. Ученик получает «отлично» за не то слово, а это хуже, чем незачёт правильного:
подрывает доверие к тренажёру.

**Правка:** применять правило подстроки только когда короткая строка ≥ 4 символов **или**
разница длин ≤ 1. Тогда «да»/«дас» пойдёт по Левенштейну (0.67 — «почти»), а «tschüss
zusammen»/«tschüss» останется 0.9, как задумано.

## 🟢 6. `grounding`: подмена текста у упражнения с прогрессом — лучше исключить

Прогресс привязан к `exercise_id`, поэтому технически ничего не рвётся. Но ученик, который
уже отвечал, при повторе увидит другой текст — а в отчёте это тот же самый пройденный пункт.
Приемлемо, пока подмена разовая; правильнее ограничить её упражнениями, у которых прогресса
ещё нет (`NOT EXISTS user_exercise_progress`). Правка дешёвая, вопрос снимается совсем.

## Про метод: моя собственная ошибка в этой проверке

Первый вариант проверки гейта я написал с `JOIN user_exercise_progress` вместо `LEFT JOIN`.
При INNER JOIN в группу попадают только упражнения, у которых прогресс уже есть, поэтому обе
части сравнения считаются по одному подмножеству и условие «пройден» становится тождественно
истинным. Вывод получился ровно обратный правде: «у всех всё пройдено».

Поймал это по несовпадению с детальным запросом (12 карточек, сделано 2 — а урок «пройден»).
Урок общий: проверку правила надо воспроизводить точной копией запроса из кода, а любой
результат «всё хорошо» проверять вторым, независимым способом.

## Порядок действий

1. Хотфикс гейта (`touchedSet`) — сегодня, это доступ живых учеников.
2. Защита `upsertLessonWord` (ORDER BY + NOT EXISTS) — до следующей обработки старого урока.
3. Подстрока в `speechMatch` — быстро и заметно ученику.
4. Предупреждение в журнал при недоборе упражнений.
5. Дальше: `user_lesson_unlocked`, порог 80%, единая локальная дата, признак предложения
